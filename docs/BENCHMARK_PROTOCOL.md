# Benchmark protocol v1

> Status: **v1.0** as of 2026-11-26. Applies to every suite in
> `jcheng-benchmark`; the repository-local formats are versioned by this
> document.

## 1. Purpose and non-goals

The protocol makes a benchmark result reproducible and comparable:

- the question, metric, sample count and threshold are declared **before** the
  dataset is collected;
- the exact suite and dataset are identified by SHA-256 in the report;
- the level and data source are part of the result, so a synthetic run cannot
  masquerade as a hardware run;
- a failed bound stays failed.

It does **not** verify how a recording was captured, certify safety, or replace
the source repository's acceptance report. A benchmark pass is a project gate,
not a safety certification.

## 2. Pre-registration

The committed suite file is the pre-registration record. Its SHA-256, recorded
in every report, identifies the exact declaration that was applied.

Rules:

1. Write the suite, including `min_samples` and every threshold, before
   collecting the dataset.
2. Cite the source of each threshold in `limitations` or in the commit message.
   A threshold copied from another repository must say where it came from and
   whether the aggregation is the same.
3. Do not edit a suite after data collection. Create a new file with a new
   `suite` id, run it, and report the new result alongside the old one.
4. Do not remove outliers, change the denominator or switch the aggregate to
   obtain a pass. Report the failed bound.
5. A run that produces `inconclusive` is a result. Record it; do not silently
   rerun until a pass appears.

## 3. Levels and data sources

| Level | Environment | Allowed `data_source` | Meaning |
|---|---|---|---|
| L0 | Contract/static | N/A | A suite cannot be L0; this level is for repository gates |
| L1 | Unit | `synthetic`, `mock` | Harness logic only |
| L2 | Mock integration | `synthetic`, `mock` | In-process or synthetic pipeline |
| L3 | Mock end-to-end | `synthetic`, `mock` | Mock gateway/topics, no hardware |
| L4 | Replay | `recorded` (or `hardware`) | Recorded data replayed offline |
| L5 | Hardware | `hardware` | Data captured on the robot in an authorized session |

The loader enforces the mapping. A suite that declares `L4` with synthetic data
is invalid and fails validation with exit code 2.

`data_source` describes the data, not the hope:

- `synthetic` — generated by a fixture or simulator.
- `mock` — produced by a mock component.
- `recorded` — exported from a recording made earlier.
- `hardware` — captured directly during the current authorized hardware
  session.

## 4. Suite format

A suite is a YAML mapping:

```yaml
schema_version: 1
suite: example-position-accuracy
title: Example position accuracy
level: L4
data_source: recorded
description: One sentence about the question and the dataset.
min_samples: 30
metrics:
  - id: position_error
    kind: position_error
    unit: mm
thresholds:
  - metric: position_error
    aggregate: p95
    op: "<="
    value: 5.0
limitations:
  - The threshold source must be stated here or in the commit message.
```

| Field | Required | Rule |
|---|---|---|
| `schema_version` | yes | Must be `1` |
| `suite` | yes | Lower-case slug matching `^[a-z][a-z0-9_-]*$`; unique in the catalogue |
| `title` | yes | Non-empty human-readable title |
| `level` | yes | `L1`–`L5`; `L0` is not a suite level |
| `data_source` | yes | `hardware`, `recorded`, `synthetic` or `mock` |
| `description` | no | Empty allowed; state the question |
| `min_samples` | yes | Integer >= 1; below it the result is `inconclusive` |
| `metrics` | yes | Non-empty list; ids unique |
| `thresholds` | no | List; empty means informational, result `inconclusive` |
| `limitations` | no | List of strings; copied into the report |

### Metric entries

| Kind | Required fields | Produces |
|---|---|---|
| `position_error` | `id`; `unit` must be `mm` if present | `count`, `mean`, `p50`, `p95`, `max`, `min` |
| `scalar` | `id`, `source`, `aggregate`, `unit` | `count`, `mean`, `p50`, `p95`, `max`, `min` |
| `success_rate` | `id`; `source` defaults to `success`; `unit` fixed to `ratio` | `count`, `rate` |

For `scalar`, `aggregate` names the primary aggregate for documentation;
thresholds may use any produced aggregate. For `success_rate`, the only
aggregate is `rate`.

### Threshold entries

```yaml
thresholds:
  - metric: position_error
    aggregate: p95
    op: "<="
    value: 5.0
```

`metric` must exist, `aggregate` must be produced by that metric, `op` must be
one of `<=`, `<`, `>=`, `>` and `value` must be a finite number. Thresholds are
evaluated exactly as written; there is no tolerance or rounding.

## 5. Dataset format

The dataset is JSON Lines: one JSON object per line, blank lines ignored.
Additional fields are allowed but are not interpreted unless a declared metric
names them.

```json
{"sample_id":"pose-001-r01","trial":"pose-001","measured_m":[0.3347,-0.0147,-0.0835],"reference_m":[0.3354,-0.0127,-0.0857],"latency_ms":54.1,"success":true}
```

| Field | Required | Rule |
|---|---|---|
| `sample_id` | yes | Non-empty string, unique across the file |
| `trial` | no | Non-empty string; reports count distinct trials |
| `measured_m` | for `position_error` | `[x, y, z]`, three finite numbers, metres |
| `reference_m` | for `position_error` | `[x, y, z]`, three finite numbers, metres |
| scalar source field | for `scalar` | Finite number; bool is not a number |
| `success` (or declared source) | for `success_rate` | JSON `true` or `false` |

One malformed line aborts the whole run with the file and line number. Rows are
never skipped to improve the denominator.

Datasets are not committed to this repository. Store them outside the tree and
record their path and SHA-256 in the report; see [EVIDENCE.md](EVIDENCE.md).

## 6. Metrics and aggregates

- **Position error** — `1000 * ||measured_m - reference_m||_2`, in millimetres,
  computed per sample.
- **Scalar** — the declared source field is read as a float for every sample.
- **Success rate** — `true_count / sample_count`; the result is a ratio in
  `[0, 1]`.

Aggregates:

- `mean` — arithmetic mean using `math.fsum`.
- `p50`, `p95` — nearest-rank percentiles: sort ascending and take the
  `ceil(p/100 * n)`-th value (1-based). No interpolation.
- `max`, `min` — extremes.
- `count` — number of samples.
- `rate` — success rate.

The nearest-rank definition is part of the protocol. A report is comparable
with another report only if both use the same aggregate definition.

## 7. Result semantics and exit codes

| Condition | Result | Exit |
|---|---|---|
| Dataset valid, `n >= min_samples`, thresholds non-empty, all pass | `pass` | 0 |
| Dataset valid, `n >= min_samples`, at least one threshold fails | `fail` | 1 |
| Dataset empty | `inconclusive` | 2 |
| `n < min_samples` | `inconclusive` | 2 |
| No thresholds declared | `inconclusive` | 2 |
| Invalid suite or dataset | error (no report) | 2 |

If a threshold fails while `n < min_samples`, the overall result is
`inconclusive`; the failed threshold is still listed in the report so it is not
hidden.

Exit code 0 means "the declared gate passed for the declared data source". It
does not mean "hardware validated", "safe" or "released".

## 8. Report format (repository-local v1)

A report is a JSON object with:

| Key | Meaning |
|---|---|
| `schema_version` | `1` |
| `report_kind` | `benchmark-report` |
| `tool` | `{name, version}` |
| `generated_at` | ISO 8601 UTC timestamp |
| `operator`, `host` | Provenance labels |
| `suite` | `id`, `title`, `level`, `data_source`, `description`, `min_samples`, `path`, `sha256` |
| `dataset` | `path`, `sha256`, `samples`, `trials` |
| `metrics` | Metric id to kind, unit, count and aggregates |
| `thresholds` | Metric, aggregate, op, value, actual, pass |
| `result`, `result_reason` | `pass`, `fail` or `inconclusive` and why |
| `limitations` | Declared limitations plus generated provenance cautions |
| `notes` | Operator notes from `--note` |

The Markdown rendering is a convenience view of the same mapping; the JSON is
the machine-readable record. The format is not a cross-repository contract. If
a second repository consumes it, propose it to `jcheng-interfaces` first.

## 9. Evidence

Reports are stored under `evidence/benchmark_<YYYYMMDD>_<slug>/` with the JSON,
the Markdown, the command, the environment and the dataset pointer. Reports are
append-only. See [EVIDENCE.md](EVIDENCE.md).

## 10. Adding a suite

1. State the question in one sentence and choose the metric kind.
2. Choose the level and data source; confirm the mapping is allowed.
3. Write the suite with `min_samples` and thresholds **before** collecting data.
4. Commit the suite. Record its SHA-256 after the run; it identifies the
   declaration.
5. Export the dataset outside the repository and record its provenance.
6. Run with `--operator`, `--host` and a `--note`; write JSON and Markdown.
7. Store the report and companion files under `evidence/`.
8. Report the result even if it is `fail` or `inconclusive`; update the roadmap
   or acceptance documents only with a linked evidence path.

## 11. Out of scope

- Live data capture, ROS subscriptions or DDS participation.
- Device access and motion commands.
- Dataset generation, editing or outlier removal.
- Safety certification and release approval.
- A cross-repository contract without promotion to `jcheng-interfaces`.
